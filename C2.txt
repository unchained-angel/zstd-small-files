# Project: Zstd Dictionary Training for Small JSON API Responses

This is an excellent, high-ROI project. For files under 10 KB (especially 1–4 KB JSON payloads), vanilla `zstd` struggles because the LZ77 sliding window hasn't "warmed up" yet, and the frame header overhead consumes a significant percentage of the file. A shared dictionary pre-loads that context.

Here is the complete development guide, from architecture to code, to benchmark it.

---

## 1. The Core Answer: How much does it improve?

Based on empirical data for small JSON API responses:
*   **Vanilla zstd (Level 3):** Usually achieves a **2x to 4x** compression ratio on 2KB–5KB JSON files. The ~18-byte frame header + block headers represent ~1-2% overhead.
*   **Dictionary-trained zstd:** Typically achieves a **5x to 10x+** compression ratio on the exact same files.
*   **The Delta:** You can expect a **40% to 60% reduction in compressed payload size** compared to vanilla zstd.
*   **Why?** The dictionary contains the literal strings (`"id":`, `"status":`, `"created_at":`) and structural patterns. Instead of storing these bytes, zstd just stores a 3-byte back-reference to the dictionary.

---

## 2. Project Architecture & Constraints Check

To satisfy your constraints (**no large per-file header, fast startup**), we must follow specific rules:

1.  **Dictionary ID:** We will embed a 4-byte Dictionary ID in the compressed frame. The client uses this to look up the dictionary in memory. This adds exactly 4 bytes of overhead per file, satisfying the "no large header" constraint.
2.  **Fast Startup:** The dictionary must be loaded into memory *once* at application startup (using `ZSTD_createDDict()`). Do not load it from disk per-request.
3.  **Sample Size:** To train a good dictionary, you need **~100 to 1,000 representative samples**. They should total at least 100x the target dictionary size.

### Phase 2: Dictionary Training
We will train a **10 KB dictionary**. (Rule of thumb: Dict size should be roughly 10KB - 100KB. Too large slows down initialization; too small misses patterns).

```python
import zstandard as zstd
import glob

def train_dictionary():
    # Load all samples into memory
    sample_files = glob.glob("samples/*.json")
    samples = []
    for path in sample_files:
        with open(path, "rb") as f:
            samples.append(f.read())

    # Train the dictionary (Target size: 10KB)
    print(f"Training dictionary on {len(samples)} samples...")
    dict_data = zstd.train_dictionary(
        max_dict_size=10 * 1024, 
        samples=samples
    )

    # Save the dictionary
    with open("api_dict.zst", "wb") as f:
        f.write(dict_data.as_bytes())
    
    print(f"Dictionary trained and saved. Size: {len(dict_data.as_bytes())} bytes")
    return dict_data

train_dictionary()
```

### Phase 3: Compression & Benchmarking
Now we test Vanilla vs. Dictionary on new, unseen small files.

```python
import zstandard as zstd
import time

def benchmark():
    # Load dictionary into memory (Do this ONCE at startup)
    with open("api_dict.zst", "rb") as f:
        dict_bytes = f.read()
    
    # Create Digested Dictionaries for ultra-fast repeated use
    cctx_dict = zstd.ZstdCompressor(dict_data=zstd.ZstdCompressionDict(dict_bytes))
    dctx_dict = zstd.ZstdDecompressor(dict_data=zstd.ZstdCompressionDict(dict_bytes))
    
    cctx_vanilla = zstd.ZstdCompressor(level=3)
    dctx_vanilla = zstd.ZstdDecompressor()

    # Generate a fresh test payload (not seen during training)
    test_payload = json.dumps({
        "request_id": "req_9999",
        "timestamp": "2026-09-18T12:05:00Z",
        "status": "success",
        "user": {"id": 42, "role": "admin", "email_verified": True},
        "payload": {"items": [{"sku": "ITEM-12", "qty": 2}]}
    }).encode('utf-8')

    print(f"\nOriginal Payload Size: {len(test_payload)} bytes")

    # --- VANILLA COMPRESSION ---
    comp_vanilla = cctx_vanilla.compress(test_payload)
    decomp_vanilla = dctx_vanilla.decompress(comp_vanilla)
    assert decomp_vanilla == test_payload
    
    # --- DICTIONARY COMPRESSION ---
    comp_dict = cctx_dict.compress(test_payload)
    decomp_dict = dctx_dict.decompress(comp_dict)
    assert decomp_dict == test_payload

    # --- RESULTS ---
    print("-" * 40)
    print(f"Vanilla Compressed:    {len(comp_vanilla)} bytes (Ratio: {len(test_payload)/len(comp_vanilla):.2f}x)")
    print(f"Dictionary Compressed: {len(comp_dict)} bytes (Ratio: {len(test_payload)/len(comp_dict):.2f}x)")
    print(f"Space Saved by Dict:   {((len(comp_vanilla) - len(comp_dict)) / len(comp_vanilla)) * 100:.1f}%")

benchmark()
```

## 5. Production Deployment Strategy

To meet your "fast startup" and "no large per-file header" constraints in production:

### Server-Side (API Gateway / Backend)
1.  **Load Once:** Read `api_dict.zst` into memory on boot. Create a digested dictionary object (e.g., `ZSTD_createCDict` in C, or `ZstdCompressionDict` in Python).
2.  **Versioning:** Append a version to your dictionary name (e.g., `api_dict_v1.zst`).
3.  **Header Management:** By default, zstd writes a 4-byte magic number and a 4-byte Dictionary ID into the frame header. This allows the client to know *which* dictionary to use without you writing custom routing logic. This is only 8 bytes total overhead.

### Client-Side (Frontend / Microservice)
1.  **Cache the Dictionary:** Fetch the dictionary once via HTTP and cache it in memory/local storage.
2.  **Routing:** When decompressing a response, read the Dictionary ID from the zstd frame header. Look up the corresponding dictionary in your local cache.
3.  **Fallback:** Always implement a fallback. If the client doesn't have the dictionary, standard zstd *cannot* decompress the payload. Your API should support a query param like `?compression=zstd_dict` vs `?compression=zstd` vs `?compression=none`.

### Dictionary Rotation (Crucial)
JSON schemas drift over time. 
1. Set up a cron job/CI pipeline to collect 1,000 recent API responses every week.
2. Retrain the dictionary.
3. If the new dictionary improves the ratio by >5%, deploy it as `v2`.
4. Keep `v1` alive on the server for 24 hours so clients who haven't fetched `v2` yet don't break.

That is a great question! Let's take a step back and look at the big picture.

### What is Zstandard (zstd)?

**Zstandard** (often just called **zstd**) is a very fast, modern tool for squishing data to make it smaller. 

You are probably familiar with `.zip` files. Zstandard is basically the modern, high-speed evolution of that idea. It was created by Facebook (specifically an engineer named Yann Collet) to solve a specific problem: how to compress huge amounts of data incredibly fast without losing any information.

**Why do we use it?**
Imagine your server needs to send a JSON file to a user's web browser. 
* If the file is 100 KB, it takes a little bit of time to travel across the internet.
* If we use **zstd**, we can squish that file down to 20 KB. It travels 5 times faster, saving bandwidth and making the website feel instant.

### Why do we need a "Dictionary" for small files?

Zstd is amazing for *large* files (like a 10 MB text document) because as it reads the file, it learns the patterns. It notices that the word "compression" appears a lot, so it creates a shortcut for it.

But your project is about **small files** (under 10 KB). 
When zstd looks at a tiny 2 KB JSON file, it doesn't have enough time or space to "learn" the patterns before the file ends. Also, zstd adds a tiny bit of "setup" data (a header) to every file. On a 10 MB file, that header is invisible. On a 2 KB file, that header takes up a noticeable percentage of the space!

**The Dictionary is a cheat sheet.**
Instead of forcing zstd to learn the patterns from scratch every single time, we **train** it in advance. 
We show it 500 examples of your API responses. It learns that the words `"user_id"`, `"status"`, and `"created_at"` appear in almost every single file. It saves these common words into a **Dictionary** (our cheat sheet).

Later, when zstd compresses a *new* tiny file, it doesn't write `"user_id"`. It just writes a tiny reference code that says *"Look at word #42 in the dictionary."* This makes tiny files shrink massively!

# What is a JSON file?

## The gist

**JSON** stands for **JavaScript Object Notation**.

Despite the name, JSON is not only for JavaScript. It is a plain-text format used by almost every programming language to store and send structured data.

A JSON file is a text file that contains data organized as **key-value pairs**.

Example:

```json
{
  "request_id": "req_1234",
  "status": "success",
  "user_id": 42,
  "email_verified": true
}
```

In this example:

```text
"request_id"
```

is a **key**.

```text
"req_1234"
```

is the **value** connected to that key.

You can think of it like a form:

```text
request_id: req_1234
status: success
user_id: 42
email_verified: true
```

but written in a strict format that computers can easily parse.

---

## The hook

Think of JSON as a **shipping label** for data.

When a server sends data to a browser or mobile app, it needs to say:

> Here is some information. This field is the user ID. This field is the status. This field is the timestamp.

JSON is the label that explains what each piece of data means.

For example, this:

```json
{
  "user_id": 42,
  "status": "success"
}
```

means:

```text
The user ID is 42.
The request status was success.
```

---

## Why JSON matters for our zstd project

Your project is about compressing **small JSON API responses**.

APIs often send data like this:

```json
{
  "request_id": "req_4821",
  "timestamp": "2026-09-19T12:00:00Z",
  "status": "success",
  "user": {
    "id": 37,
    "role": "admin",
    "email_verified": true
  }
}
```

Notice that the **keys repeat** in almost every response:

```text
"request_id"
"timestamp"
"status"
"user"
"id"
"role"
"email_verified"
```

That repetition is exactly what a zstd dictionary can exploit.

If every API response contains `"request_id"`, the dictionary can learn that pattern and replace it with a much smaller internal reference.

That is why JSON is a great candidate for dictionary compression.

---

## The pitfalls

### Pitfall 1: JSON is not the same as a Python dictionary

JSON looks similar to Python dictionaries, but they are not identical.

Python dictionary:

```python
{
    "status": "success",
    "email_verified": True,
    "user_id": 42
}
```

JSON:

```json
{
  "status": "success",
  "email_verified": true,
  "user_id": 42
}
```

Notice:

```text
Python uses True
JSON uses true
```

Python uses:

```text
True, False, None
```

JSON uses:

```text
true, false, null
```

### Pitfall 2: JSON keys must be strings

This is valid JSON:

```json
{
  "42": "answer"
}
```

This is not valid JSON:

```json
{
  42: "answer"
}
```

The key must be surrounded by double quotes.

### Pitfall 3: JSON is text, so it can be verbose

JSON is easy for humans to read, but that readability creates repetition.

For example:

```json
{
  "user_id": 1,
  "user_name": "alice",
  "user_email": "alice@example.com"
}
```

The word `user_` appears three times.

That is not a problem for humans, but for compression it is an opportunity.

# Step 3: Train the dictionary

## Phase 1: The Gist

We will give zstd many example JSON files. It will study them and build a small binary dictionary containing common patterns.

The main idea:

> Train a small shared dictionary from many small JSON samples so future small JSON files can be compressed much more efficiently.

In this step, we will create a Python script that:

1. reads all files inside the `samples/` folder,
2. trains a zstd dictionary from them,
3. saves the dictionary as `dictionary.bin`.

---

## Phase 2: The Pitfalls

### Pitfall 1: Training on unrepresentative samples

A dictionary only helps if it matches the future data.

If we train on weather API responses but later compress payment API responses, the dictionary may not help much.

**Self-correction script:**

> Are these samples similar to the real small JSON responses I want to compress?

For this project, our generated samples are intentionally similar to small API responses.

---

### Pitfall 2: Making the dictionary too large

A larger dictionary can learn more patterns, but it also costs more memory and startup time.

Your constraint is:

```text
fast startup
```

So we will use a modest dictionary size:

```text
10 KB
```

That is a good starting point for small JSON files.

**Self-correction script:**

> Is the dictionary small enough to load quickly and send or store easily?

---

### Pitfall 3: Forgetting that decompression needs the same dictionary

Dictionary compression is not magic.

If you compress with a dictionary, you must decompress with the same dictionary.

Minimal pair:

```text
Vanilla zstd:
compressor and decompressor only need the compressed data.

Dictionary zstd:
compressor and decompressor need both the compressed data and the dictionary.
```

This is important for real API design.

---

## Phase 3: The Hook

Think of the dictionary like a **shared phrasebook**.

Suppose every API response contains phrases like:

```text
"request_id"
"timestamp"
"status"
"user"
"payload"
```

Without a dictionary, zstd has to write those phrases again and again.

With a dictionary, both compressor and decompressor already know the phrasebook.

So instead of writing:

```text
"request_id"
```

the compressed data can say something like:

```text
use phrase #47 from the phrasebook
```

That reference can be much smaller than the original text.

### Where the analogy breaks down

A real phrasebook is useful for many languages and conversations.

A zstd dictionary is specialized. If the JSON structure changes a lot, the dictionary becomes less useful.

```text
compression ratio on files under 10 KB
```

```python
import json
import random
import zstandard as zstd
import pathlib

# ─── Configuration ───────────────────────────────────────────────
NUM_TEST_FILES = 100
COMPRESSION_LEVEL = 3
MAX_FILE_SIZE = 10 * 1024  # Only test files under 10 KB

# ─── Generate fresh test data ────────────────────────────────────
def generate_test_sample():
    """Generate a new small JSON API response (different from training)."""
    return json.dumps({
        "request_id": f"test_{random.randint(10000, 99999)}",
        "timestamp": "2026-09-19T14:30:00Z",
        "status": random.choice(["success", "pending", "failed", "timeout"]),
        "user": {
            "id": random.randint(1, 10000),
            "role": random.choice(["admin", "user", "guest", "moderator"]),
            "email_verified": random.choice([True, False])
        },
        "payload": {
            "items": [
                {
                    "sku": f"PROD-{random.randint(100, 999)}",
                    "qty": random.randint(1, 20),
                    "price": round(random.uniform(1.0, 500.0), 2)
                }
                for _ in range(random.randint(1, 5))
            ],
            "currency": random.choice(["USD", "EUR", "GBP"])
        }
    }).encode("utf-8")

print(f"Generating {NUM_TEST_FILES} fresh test files...")
test_files = []
for i in range(NUM_TEST_FILES):
    data = generate_test_sample()
    if len(data) < MAX_FILE_SIZE:
        test_files.append(data)

print(f"Kept {len(test_files)} files under {MAX_FILE_SIZE} bytes")

# ─── Load dictionary ─────────────────────────────────────────────
dict_path = pathlib.Path("dictionary.bin")
dict_data = zstd.ZstdCompressionDict(dict_path.read_bytes())

# ─── Set up compressors ──────────────────────────────────────────
vanilla_compressor = zstd.ZstdCompressor(level=COMPRESSION_LEVEL)
dict_compressor = zstd.ZstdCompressor(level=COMPRESSION_LEVEL, dict_data=dict_data)

vanilla_decompressor = zstd.ZstdDecompressor()
dict_decompressor = zstd.ZstdDecompressor(dict_data=dict_data)

# ─── Run benchmark ───────────────────────────────────────────────
total_original = 0
total_vanilla = 0
total_dict = 0

print("\nRunning benchmark...")
print("-" * 60)

for i, original in enumerate(test_files):
    # Compress with vanilla zstd
    compressed_vanilla = vanilla_compressor.compress(original)

    # Compress with dictionary zstd
    compressed_dict = dict_compressor.compress(original)

    # Verify decompression
    assert vanilla_decompressor.decompress(compressed_vanilla) == original
    assert dict_decompressor.decompress(compressed_dict) == original

    total_original += len(original)
    total_vanilla += len(compressed_vanilla)
    total_dict += len(compressed_dict)

# ─── Report results ──────────────────────────────────────────────
vanilla_ratio = total_original / total_vanilla
dict_ratio = total_original / total_dict
improvement = ((total_vanilla - total_dict) / total_vanilla) * 100

print(f"\n{'Metric':<35} {'Vanilla zstd':<15} {'Dictionary zstd':<15}")
print("-" * 65)
print(f"{'Total original size (bytes)':<35} {total_original:<15} {total_original:<15}")
print(f"{'Total compressed size (bytes)':<35} {total_vanilla:<15} {total_dict:<15}")
print(f"{'Compression ratio':<35} {vanilla_ratio:<15.2f} {dict_ratio:<15.2f}")
print(f"{'Space saved vs original (%)':<35} {(1 - total_vanilla/total_original)*100:<15.1f} {(1 - total_dict/total_original)*100:<15.1f}")
print("-" * 65)
print(f"\nDictionary zstd is {improvement:.1f}% smaller than vanilla zstd")
print(f"Average file size: {total_original // len(test_files)} bytes")
```

### Interpreting Your Results

Look at the average file size in your test: **341 bytes**. 
At this tiny size, **Vanilla zstd** struggles. It only saved 32.5% of the space (a 1.48x ratio). Why? Because every single compressed file requires a "frame header" (setup metadata). # 5.3 Create the compression tool

Now create the Python script:

```bash
nano compress.py
```

Paste this code:

```python
import pathlib
import sys

import zstandard as zstd


def main():
    # The user must provide:
    # python compress.py input.json output.zst
    if len(sys.argv) != 3:
        print("Usage: python compress.py input_file output_file")
        print("Example: python compress.py example.json example.zst")
        sys.exit(1)

    input_path = pathlib.Path(sys.argv[1])
    output_path = pathlib.Path(sys.argv[2])
    dictionary_path = pathlib.Path("dictionary.bin")

    if not input_path.exists():
        print(f"Error: input file not found: {input_path}")
        sys.exit(1)

    if not dictionary_path.exists():
        print("Error: dictionary.bin not found.")
        print("Make sure you are inside the project folder.")
        sys.exit(1)

    # Load the trained dictionary into memory
    dictionary_bytes = dictionary_path.read_bytes()
    dictionary = zstd.ZstdCompressionDict(dictionary_bytes)

    # Create a compressor that uses the dictionary
    compressor = zstd.ZstdCompressor(level=3, dict_data=dictionary)

    # Read the original JSON file as bytes
    original_data = input_path.read_bytes()

    # Compress it
    compressed_data = compressor.compress(original_data)

    # Save compressed output
    output_path.write_bytes(compressed_data)

    # Print simple results
    print(f"Dictionary: {dictionary_path}")
    print(f"Input file: {input_path}")
    print(f"Output file: {output_path}")
    print(f"Original size: {len(original_data)} bytes")
    print(f"Compressed size: {len(compressed_data)} bytes")

    if len(compressed_data) < len(original_data):
        saved = (1 - len(compressed_data) / len(original_data)) * 100
        print(f"Space saved: {saved:.1f}%")
    else:
        print("Compressed file is not smaller than original.")


if __name__ == "__main__":
    main()
```

```python
    print(f"Dictionary: {dictionary_path}")
    print(f"Compressed input: {input_path}")
    print(f"Recovered output: {output_path}")
    print(f"Compressed size: {len(compressed_data)} bytes")
```

# Step 7: Dictionary Versioning and IDs

## Phase 1: The Gist
In a real API, your JSON schema will change over time. You will eventually train a new dictionary (`dictionary_v2.bin`). But when a client receives a compressed `.zst` file, how does it know *which* dictionary to use without you manually telling it? 

Zstandard solves this by embedding a tiny **4-byte Dictionary ID** into the compressed file's header. 

**One-sentence compression:** We will inspect our compressed file to reveal the hidden Dictionary ID, which acts as a routing tag so the decompressor automatically knows which dictionary to load.

## Phase 2: The Pitfalls

### The Trap: Hardcoding the dictionary path
Beginners often write decompression code that blindly assumes the dictionary is always named `dictionary.bin`. 

**The Minimal Pair:**
*   **Hardcoded:** `decompress.py` always loads `dictionary.bin`. If the server upgrades to `v2`, the client crashes.
*   **Dynamic (Dictionary ID):** `decompress.py` reads the 4-byte ID from the compressed file, looks up the ID in a local registry, and loads `dictionary_v2.bin` automatically.

**Self-Correction Script:**
> "If I rename my dictionary file right now, will my decompressor still work, or will it break because it's looking for a specific filename?"

## Phase 3: The Hook
Think of the Dictionary ID like a **luggage claim ticket**. 

When you check a bag at the airport, the airline doesn't staple your whole suitcase to your boarding pass. They just give you a tiny paper ticket with a number on it (e.g., `849201`). 
When you arrive at your destination, you look at the ticket, look at the carousel, and grab the bag that matches your number.

The compressed `.zst` file doesn't carry the whole dictionary. It just carries a tiny 4-byte "ticket" (the Dictionary ID). The decompressor reads the ticket and grabs the matching dictionary from its memory.

# Step 8: Build a smart decompressor with a registry

## Phase 1: The Gist

We will build a smarter decompression tool.

Instead of always loading:

```text
dictionary.bin
```

it will:

1. inspect the compressed file,
2. read its Dictionary ID,
3. look up that ID in a small registry file,
4. load the correct dictionary,
5. decompress the file.

One-sentence version:

> We are building a client-side decompressor that automatically chooses the correct dictionary based on the Dictionary ID embedded in the compressed file.

---

## Phase 2: The Pitfalls

### Pitfall 1: Hardcoding one dictionary filename

A beginner decompressor often says:

```text
Always load dictionary.bin
```

But in a real system, you may have:

```text
dictionary_v1.bin
dictionary_v2.bin
dictionary_v3.bin
```

If the server starts compressing with version 2, but the client still loads version 1, decompression can fail or produce wrong results.

### Minimal pair

```text
Hardcoded decompressor:
Always loads dictionary.bin

Registry-based decompressor:
Reads the Dictionary ID and loads the matching dictionary file
```

### Self-correction script

Ask:

> Does my decompressor know which dictionary version to use, or am I just hoping the filename is correct?

---

### Pitfall 2: Thinking dictionary ID is the filename

The Dictionary ID is not a filename.

This is a Dictionary ID:

```text
1163550679
```

This is a filename:

```text
dictionary.bin
```

The registry connects them:

```json
{
  "1163550679": "dictionary.bin"
}
```

---

### Pitfall 3: Forgetting vanilla fallback

If the Dictionary ID is:

```text
0
```

then no dictionary is needed.

A smart decompressor should fall back to normal zstd decompression.

---

## Phase 3: The Hook

Think of the registry as a **coat check**.

The compressed file arrives with a ticket:

```text
Dictionary ID: 1163550679
```

The decompressor goes to the coat check, shows the ticket, and receives the matching dictionary file.

If the ticket says:

```text
0
```

that means:

> “No coat was checked in. You can proceed without one.”

### Where the analogy breaks down

A coat check gives you back a physical coat.

Here, the registry does not send the dictionary inside every compressed file. It only tells the decompressor where to find the dictionary locally.

In a real client, if the dictionary is missing, the client may need to download it from the server first.

---

## Phase 4: Why It Matters

This step moves the project from a local experiment toward a real API system.

In production:

```text
Server compresses with dictionary version 1
Client receives compressed payload
Client reads Dictionary ID
Client loads dictionary version 1
Client decompresses
```

Later:

```text
Server compresses with dictionary version 2
Client receives compressed payload
Client reads Dictionary ID
Client notices it needs version 2
Client downloads dictionary version 2
Client decompresses
```

This is how you get the compression benefit without attaching the whole dictionary to every response.

# 8.2 Create the smart decompressor

Create the script:

```bash
nano smart_decompress.py
```

Paste this code:

```python
import json
import pathlib
import sys

import zstandard as zstd


REGISTRY_PATH = pathlib.Path("registry.json")


def load_registry():
    if not REGISTRY_PATH.exists():
        return {}

    text = REGISTRY_PATH.read_text()
    return json.loads(text)


def main():
    # Expected:
    # python smart_decompress.py input.zst output.json
    if len(sys.argv) != 3:
        print("Usage: python smart_decompress.py input_file output_file")
        print("Example: python smart_decompress.py example.zst recovered_smart.json")
        sys.exit(1)

    input_path = pathlib.Path(sys.argv[1])
    output_path = pathlib.Path(sys.argv[2])

    if not input_path.exists():
        print(f"Error: input file not found: {input_path}")
        sys.exit(1)

    compressed_data = input_path.read_bytes()

    # Read the zstd frame header
    params = zstd.get_frame_parameters(compressed_data)
    dictionary_id = params.dict_id

    print(f"Input file: {input_path}")
    print(f"Dictionary ID from frame: {dictionary_id}")

    if dictionary_id == 0:
        # Vanilla zstd fallback
        print("No dictionary required. Using vanilla zstd decompression.")
        decompressor = zstd.ZstdDecompressor()
        dictionary_source = "none"
    else:
        # Dictionary lookup
        registry = load_registry()

        dictionary_file = registry.get(str(dictionary_id))

        if dictionary_file is None:
            print(f"Error: No dictionary registered for ID {dictionary_id}")
            print("Add it to registry.json, for example:")
            print(f'{{"{dictionary_id}": "dictionary.bin"}}')
            sys.exit(1)

        dictionary_path = pathlib.Path(dictionary_file)

        if not dictionary_path.exists():
            print(f"Error: dictionary file not found: {dictionary_path}")
            sys.exit(1)

        dictionary_bytes = dictionary_path.read_bytes()
        dictionary = zstd.ZstdCompressionDict(dictionary_bytes)

        print(f"Using dictionary file: {dictionary_path}")
        decompressor = zstd.ZstdDecompressor(dict_data=dictionary)
        dictionary_source = str(dictionary_path)

    # Decompress
    try:
        recovered_data = decompressor.decompress(compressed_data)
    except Exception as error:
        print("Decompression failed.")
        print(f"Error: {error}")
        sys.exit(1)

    output_path.write_bytes(recovered_data)

    print(f"Recovered output: {output_path}")
    print(f"Compressed size: {len(compressed_data)} bytes")
    print(f"Recovered size: {len(recovered_data)} bytes")
    print(f"Dictionary used: {dictionary_source}")
    print("Decompression successful.")


if __name__ == "__main__":
    main()
```

```text
Enter
Ctrl + X
```
